# MinuteFlow Windows 开发与双平台更新计划

计划日期：2026-10-10。基线：现有 Mac v0.12.1。本文是实施与验收要求，不能作为已经通过 Windows 实机测试的证明；实际状态见功能矩阵与独立验证记录。

## 1. 产品目标与路线

保留现有 Swift/SwiftUI Mac 原生版本，新增 C#/.NET Windows 桌面版本。两端使用同一产品版本、功能需求、数据契约、测试用例和 GitHub Release；系统采集与界面分别维护。用户已允许两套平台应用，因此本次无需为发布 Windows 版重写已可用的 Mac UI。

Windows 使用 WPF；音频使用 NAudio 封装 WASAPI loopback 与麦克风采集。无系统依赖的会议、转写、AI、存储和录音状态规则位于 `windows/MinuteFlow.Core`；WPF、DPAPI、WASAPI、设备和托盘位于 `windows/MinuteFlow.Windows`。实现应固定依赖版本，不依赖目标电脑安装开发 SDK。

这条路线共享产品契约和验收用例，不意味着 Swift 与 C# 已共享全部运行源码。以后业务功能改动必须同时检查两端；不得把“同版本号”当作“自动实现功能一致”。将来是否统一界面，应依据 Windows 试用结果另行评估。

Windows 首先提供 win-x64 自包含包；ARM64 仅在独立构建与设备验证通过后列入支持范围。WPF 是 Windows 专用框架；WASAPI loopback 可录制渲染设备的系统混音，受设备状态与受保护音频限制，不能承诺所有声音都可捕获。[WPF 官方说明](https://learn.microsoft.com/en-us/dotnet/desktop/wpf/overview/)、[WASAPI 官方说明](https://learn.microsoft.com/en-us/windows/win32/coreaudio/loopback-recording)。

## 2. 模块与交付顺序

|阶段|交付|依赖/完成条件|
|---|---|---|
|P0 契约|本计划、功能矩阵、统一版本文件、历史 Mac 兼容样例|字段、枚举、秒/帧单位与重定位规则明确|
|P1 核心|状态机、目录存储、凭据抽象、ASR/文本客户端、分段与静音保护|无音频硬件的确定性测试通过|
|P2 系统|双路采集、设备枚举、时间轴、录音文件、混音、播放、DPAPI|Windows 构建成功，并经 Windows 音频实机检查|
|P3 工作流|完整 UI、实时/事后转写、AI、历史管理、托盘、诊断|每个可见按钮执行实际功能；错误可处理、取消有效|
|P4 双平台|Mac 兼容改进、公共夹具、同版本构建、发布脚本|两端读取交换样例，Mac 回归通过，Windows 独立检查通过|
|P5 发布|同 tag 的 Mac/Windows 安装包、校验和、更新记录|实际包启动/升级验证和硬件门禁记录齐全|

各阶段允许并行开发，但 P2/P3 的占位 UI、模拟音频或 Linux/Mac 上编译成功不能替代 P5。首次 Windows 发布如实标为 preview，直到实机门禁完成；已有 Mac 稳定版不因另一端尚待实测而被称为未验证。

## 3. 完整功能要求

### 3.1 录音与回放

- 声音来源：仅麦克风、仅系统声音、两者；显示实际设备与音量，不把权限通过当作录到了声音。
- 开始、暂停、恢复、停止、退出前保存。有效时长采用单调时钟；暂停不计入会议录音时间。禁止重复开始和停止保存过程中重新开始。
- 两路原文件持续保留。捕获格式分别标准化，按共同有效时间轴记录每段源帧与目标帧映射；启动差、暂停、缺口、单路断开均用静音对齐。单路故障提示并保留另一轨，不能静默停止全部录音。
- 结束后生成统一完整回放；流式/分块混音避免把一整晚音频载入内存。预留混音余量、峰值保护，临时输出验证后原子提交，不覆盖原轨。
- Windows 原轨可使用正确编码的 WAV；若提供 M4A，必须使用真实 AAC 编码，不能仅改扩展名。跨平台读取支持已声明的真实音频格式。压缩格式差异在矩阵中明确。
- 确认实际保存后再显示完成。混音失败可重试，原轨保持可播放。文件定位使用 Explorer/Finder，完整回放及原轨均可操作。

### 3.2 实时与事后转写

- 连续讲话约 3 秒提供临时预览，预览不保存为最终逐字稿；约 0.7 秒自然停顿形成最终片段。
- 动态估计底噪；连续讲话 15 秒安全切片，约 450 ms 重叠并去重；约 40 秒可读段落上限。异步乱序响应按音频时间排序，不打乱讲话顺序。
- 最多两个上传任务并发、有界队列、超时；429/5xx/网络问题有限重试，401/403 直接提示配置；收尾时间有上限。未完成最终片段保留本机重试信息，预览不保留。
- 一个自定义 AI 配置页面：Base URL、Token、ASR 模型、文本模型和开关。Token Plan 使用 `api-key`、`/chat/completions`、`input_audio.data = data:audio/wav;base64,...`；其他兼容服务使用 Bearer、`/audio/transcriptions` multipart，不能混用。
- 真实连接测试分别检查音频识别和文本模型，说明返回错误与耗时；测试音频不混入用户会议。
- 录音期间保存有效配置后立即热启动/替换实时识别；缺失 Token 时录音仍可保存，恢复配置后仍能补全之前缺口。
- 已保存音频支持整段事后转写、进度、取消和失败继续。单个静音片段跳过；全段无文字才显示无有效语音。取消必须停止切片、上传与后续保存；不能覆盖用户已编辑文本而不说明。
- 原识别文本、用户编辑文本、基础校正分别保留；ASR 原始片段、边界原因和重叠信息为识别证据。清理协议标记，不能把清理误当模型校正。
- 本地说话人分析、带时间戳逐字稿、说话人改名必须独立实现或明确标为未完成。`系统声音/麦克风` 是来源，不等同于说话人声学区分。

### 3.3 AI 与历史会议

- 按用户开关自动/手动生成纪要、AI 排版文稿和主题；长文本先分段摘要再合并，防止超上下文。异步结果按稳定会议 ID 归属，不能写入当前另一场会议。
- 自动主题只替换未命名标题；保留用户手工名称。批量历史主题整理以已有文字为依据，空逐字稿跳过，不编造主题。
- 左侧显示主题、开始时间、时长、可选地点；主区紧凑录音控制，逐字稿固定高度单一整体滚动区域。
- 已保存标题默认只读，双击进入编辑；回车/失焦统一提交，Esc 可撤销草稿。右侧、左侧改名、AI 主题通过同一路径同步实际目录与元数据。
- 同名/非法路径名处理后，实际文件夹名与显示标题一致。录音、混音、转写正在操作目录时禁用改名/删除或稳定协调，防止路径失效。
- 每场会议扁平目录统一放置原轨、完整回放、逐字稿、纪要和 AI 文稿；稳定 UUID 存于隐藏元数据。删除有明确确认与可恢复路径优先。
- 查看、切换、加载及重复保存相同内容不修改文件 mtime；只有实际编辑或生成新内容写入。崩溃后的活动记录恢复为中断，原文件保留。
- 地点记录仅显式启用并获系统授权后执行；拒绝定位不阻断录音。Windows 定位需要独立平台实现，暂不可用时如实显示差异。

### 3.4 防忘关与性能

- 默认连续 30 分钟无有效声音自动暂停，可选 60 分钟/关闭；检测两路实际音量，与 AI 成败无关。暂停后弹出继续、结束保存、保持暂停选项；不因声音恢复自动开始。
- 开始/恢复重新计算无声窗口；暂停、准备、保存状态不重复触发。持续音乐/噪音可阻止无声触发，说明这一边界。
- 音频回调只处理有界采样/写入/队列，不执行 UI、网络或目录扫描；UI 音量受限刷新、计时按秒更新；全文与元数据变更防抖保存、内容相同跳过写入。
- 长音频切片与混音可取消、分块处理；长历史和逐字稿使用虚拟化/合理刷新，避免一次生成全部编辑控件。

### 3.5 凭据、隐私与系统交互

- Windows Token 用 DPAPI CurrentUser 保护，默认应用配置目录与会议目录分离；保存后回读验证，重启加载成功但输入框不回显。[ProtectedData 官方说明](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.protecteddata?view=windowsdesktop-10.0)。
- 凭据失败明确提示，禁止明文静默回退。公开日志、崩溃信息、JSON、Git、发布包、交换会议不带 Token。
- 单一连接、用户显式保存/删除 Token；不把空白未改的密码框当作删除已保存凭据。
- Windows 麦克风权限/设备不可用给可行动提示；打开窗口或读取配置不启动采集。五秒自检确认两路是否有音频，分别回放。
- 托盘能开主窗、暂停/恢复、停止，状态与主窗一致。设备变化、休眠恢复、关闭主窗/退出行为须实测；任何失败均保留已录音频。

## 4. 数据契约与迁移

1. `.minuteflow-session.json` 使用现有 Swift camelCase 字段，UUID 字符串、ISO8601 时间、秒为 duration。枚举保留 `system/microphone/both` 和 `idle/preparing/recording/paused/saving/completed/interrupted/failed`，混音状态 `queued/processing/ready/degraded/failed`。
2. `逐字稿.json` 保留段落数组结构及 `id/startTime/endTime/text/originalText/normalizedText/source/isFinal/confidence/recognitionFragments/boundaryReason/speakerID`；来源 `system/microphone/mixed`。识别片段时间同为秒。
3. `混音时间轴.json` version=1，48000 帧/秒目标时间轴，`logicalDurationFrames` 和 track epochs 的帧位置采用 64 位整数。
4. 现有 Mac 元数据有绝对 `file:` URL；跨系统导入时只在该会议目录内根据安全相对路径或受控文件名重定位，拒绝路径穿越。导出新路径须两端兼容读取。未知字段容忍并尽量保留，不能靠反序列化默认值清空已有结果。
5. 迁移前备份/复制，读旧数据后首次必要迁移可写入；正常查看不反复迁移。夹具含 Mac flat/legacy、多语言与同名、可选字段缺失和 Windows 路径边界。
6. Token、位置授权和设备 ID 属各机器本地配置，不随会议导出。会议目录可复制交换，不承诺云端同步或两台机器同时编辑同一目录。

## 5. 独立验证与验收门槛

|门禁|必须提供的证据|不接受的替代|
|核心自动化|协议实际请求断言、状态/暂停时间轴、混音脉冲定位、mtime/重命名/路径、静音保护、取消/失败继续、历史JSON样例|只检查按钮/方法存在|
|Windows 构建|真实 Windows runner 完整 WPF 编译与 win-x64 publish，产物清单与校验和|只在 Mac 编译 Core|
|Windows 启动与凭据|自包含包新用户可启动，DPAPI 保存/重启/删除/读取失败检查|内存假凭据通过|
|Windows 音频实机|系统音+讲话双路/单路、暂停恢复同步、耳机切换/断开、休眠恢复、五秒自检、实际回放与峰值|CI 无声机器/生成WAV|
|远程服务|用户授权配置下真实 ASR/总结测试；401/429/网络异常和录音中修复配置|HTTP mock 作为真实连通结论|
|长录音|至少一小时双路文件大小/内存/最终回放检查；静音阈值测试与主动恢复|缩短时钟的单元测试代替实测|
|Mac 回归|现有核心检查通过、应用编译、历史只读与改名不回归、原采集仍可用|只发布旧二进制而宣称已验证新代码|
|独立审查|验证 agent 检查实现与矩阵，逐项记录通过/未通过/待实机|实现者自述100%无问题|

没有 Windows 音频硬件环境时应完成源码、构建和合成验证，再交付明确带实测待办的 preview；不得表示已达稳定全功能验收。计划中的功能未实现应列清单，不隐藏在“兼容 Windows”描述下。

## 6. 以后每次更新的双平台流程

1. 一份需求列明 Mac/Windows 的影响与允许的平台差异；功能矩阵随代码一起更新。
2. 公共 version 文件为唯一版本来源；Mac CFBundleShortVersionString、Windows 项目版本和安装产物使用相同版本。
3. 同一提交触发 Mac 检查/构建及 Windows Core 测试/WPF 发布；任何一端失败不生成双平台稳定 Release。
4. 缺陷修复两端分别确认适用性；仅系统特有修复另一端写“不适用”，不能假装两端都改了相同代码。
5. 一个 Git tag / GitHub Release 同时含 Mac ZIP、Windows 自包含包、SHA256 和双平台更新记录。签名/公证/Authenticode 是否完成如实注明；不把本机自签名当广泛受信任签名。
6. 默认以手工选择安装新版本方式交付；自动下载更新需要单独实现安全更新验证，不随便引入。安装与卸载程序保留用户数据与本机凭据，旧包清理可恢复。
7. 每次大改音频路径复跑硬件清单；纯界面/文案修复仅做对应检查，避免重复无关验证。稳定 Release 的最终 gate 必须反映本次证据，不照抄旧报告。

## 7. 本次分工

- 计划 agent：核对 Mac 基线、输出完整计划与功能矩阵，向实现者和验证者同步契约。
- 实现 agent：Windows Core、WPF 与 WASAPI/DPAPI 实现；记录真实平台差异与尚未完成项。
- 验证 agent：独立测试与代码审查，维护检查结果，发现问题交回实现者修复。
- 主 agent：Mac 兼容与版本/CI/打包集成，检查无秘密或会议数据进入仓库，汇总发布证据并推送 GitHub。

本计划不替代用户的 Windows 设备实测。功能矩阵初始 Windows 状态均是开发目标，实施结束后必须依据代码、测试及产物更新。
